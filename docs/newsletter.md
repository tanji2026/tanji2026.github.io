# 碳吉筆記電子報

## 管理方式

1. 先在「碳吉筆記」發布文章。文章草稿不會出現在電子報候選清單，發布文章也不會寄信。
2. 進入「電子報管理」，勾選要收錄的公開文章，按「彙整選擇文章」。下一期會帶入尚未寄過、已選擇收錄的文章。
3. 編輯本期主旨、前言、文章標題、摘要及排序。這些修改只影響電子報，不修改原文章。
4. 儲存並預覽整期；可寄整期測試信至管理員信箱。畫面、測試信及正式信共用同一個模板。
5. 按「核准並排定週一寄送」。系統保存核准快照，於畫面顯示的週一 08:00（Asia/Taipei）開始寄送。這個按鈕不會立即群發。
6. 需要修改核准內容時，先撤回核准，再儲存、預覽並重新核准。已開始正式寄出的期別不能改稿或撤回。

沒有新文章、沒有已儲存期別，或沒有核准，都不寄信、不增加期號。不會自動核准任何一期。
已核准後修改原文章，不會改變信中的標題、摘要或前言；若文章下架，寄送會暫停，避免寄出失效連結。

## 發行與補寄

- 每週一 08:00 的 `weeklyNewsletter` 只啟動該週已核准的期別。文章發布沒有 Firestore 寄信觸發器。
- `retryNewsletter` 每 15 分鐘續寄已啟動的期別；不會啟動未核准或尚未到期的電子報。
- 每批最多 20 人，每位收件人獨立寄送，不使用 BCC 大包群發。首次啟動保存本期收件名單，去除重複地址，寄送前再次檢查退訂狀態。
- 期號由全站計數器依正式發行累計，不按日期或年度歸零。第一位收件人被郵件服務接受後才正式累計；零收件人、全部退訂或完全未被接受不消耗期號。
- 明確未被郵件服務接受的對象，至少間隔 30 分鐘補寄，最多自動嘗試 5 次。人工重試也只處理失敗對象，沿用同一期號及快照。
- SMTP 超時或「郵件已被接受、寫入紀錄時中斷」無法保證 exactly-once。這類對象標記為待核對，停止自動重寄；管理員查閱 Gmail 紀錄並填寫依據後，才可標記成功或安排補寄。固定 Message-ID 方便核對，並不冒稱郵件服務支援冪等。
- 完全寄送失敗的期別會保留預留期號，避免下一期搶用；可核對後補寄，或在沒有已寄出／待確認對象時取消，釋放期號。前一期尚未正式發行且仍佔用預留期號時，後端會阻止核准新一期並提示先處理前一期。
- 「已接受」表示 SMTP 服務接受，不保證收件匣投遞、閱讀或不進垃圾郵件。Gmail 仍有帳號配額；本版單期最多 2,000 個訂閱文件、30 篇文章，超限會停止，不會截斷群發。

新信件使用隨機 token 的退訂連結。GET 只顯示確認頁，POST 才退訂，避免信箱預覽器自動退訂。
舊的 email 退訂連結保留確認頁相容處理。

## 資料與相容性

- `newsletterSelections/{noteId}`：是否選擇收錄。
- `newsletterIssues/{week-YYYY-MM-DD}`：草稿、修訂號、核准快照、固定排程、期號及進度。
- `newsletterIssues/{id}/deliveries/{emailHash}`：個別寄送狀態、嘗試次數與人工核對依據。
- `newsletterArticles/{noteId}`：保留於哪一期／已在哪一期寄過。
- `newsletterMeta/counter`：累計正式期號與尚未發行的預留期別。
- `newsletterOptOut/{emailHash}`：退訂 token，僅後端可讀寫。

以上集合全部沿用 Firestore 的 default-deny。管理介面經過 `newsletterAdmin`，檢查指定信箱、已驗證信箱、Google 登入與撤銷狀態後才由 Admin SDK 操作。
沒有增加訪客資料庫讀寫權限，也沒有允許前端直接修改核准、期號或寄送紀錄。

`site/public`、`site/draft`、`history`、競賽作品、探索方向、分類及媒體不重建、不遷移。
文章編輯器只保存文章欄位，清除 UI 狀態欄位，且保持 `noteDrafts`／`notes` 分離。
舊版公開文章的 `newsletterSentAt`、`newsletterCount` 在重發佈時原樣保留；規則只允許原有值，不允許偽造或改寫寄送標記，草稿不接受這些欄位。舊文章下架前會將既有寄送證據保留到後端紀錄，重新發布也不會被誤認為尚未寄過；只有公開版本的舊文章，下架時先建立草稿，保留內文。
舊 `sendNewsletter` URL 保留但回傳 410，不再接受單篇測試或立即群發，避免舊分頁繞過核准。
社群連結仍由「關於碳吉」顯示，未移動到「聯絡我們」。

## 驗證

```sh
npm ci --ignore-scripts
npm ci --prefix functions --ignore-scripts
npm test
npm run test:share
```

`npm test` 包含原有前台／後台回歸、舊資料修復，以及電子報排程、核准、快照、期號、部分失敗、併發、郵件結果不明與管理介面的隔離測試。
所有郵件均使用替身；不讀取任何真實郵件設定或 Firebase 憑證。

權限測試另外使用 Firestore Emulator（固定 localhost:8080、專案 `demo-tanji-newsletter`）。可暫時安裝測試相依套件，無須變更網站依賴：

```sh
npm install --no-save --package-lock=false --ignore-scripts @firebase/rules-unit-testing@6.0.0 firebase@13.1.0
npm run test:rules:newsletter
```

此權限測試需要先啟動本機 Firestore Emulator；不接受正式專案或遠端 host。
